# 执行工作流

## 1. 阶段定义

一次完整任务包含五个可执行阶段和两个界面阶段：

| 顺序 | 阶段 | 主要产物 | 完成门禁 |
|---:|---|---|---|
| 1 | requirement | 原始需求 | 项目归属和输入校验通过 |
| 2 | mobile-spec | Proposal、Specs、Design、Review、Tasks | Mobile Spec Gate 全部通过 |
| 3 | preview | 3 份 SVG 视觉方案和 preview set | 用户确认当前集合中的有效方案 |
| 4 | implementation | SiteManifest、生成文件账本和源码 | Schema、路径、路由与必需文件校验通过 |
| 5 | build | 生产构建和真实日志 | `npm ci` 与生产构建成功 |
| 6 | deployment | 外部 URL 和健康检查证据 | URL 合法且公网检查通过 |
| 7 | delivered | 三项 evidence 与交付 URL | Mobile Spec、build、deploy evidence 均为真 |

## 2. 预览确认门禁

Mobile Spec 通过后，Runner 先生成 3 份需求专属 SVG，再返回 `awaiting_approval`。此时：

- 不调用 Codex；
- 不写正式网站源码；
- 不执行构建和部署；
- 释放共享 Runner 并发名额；
- D1 保存 pending 审批状态。

控制面只读取当前 preview set 的 3 份 SVG，并复用这些资产提供卡片和单张沉浸预览。沉浸视图可切换桌面 `1440×900`、平板 `768×1024`、手机 `390×844` 模拟画布，也可在当前批次内前后切换方向；这些操作不重新生成 SVG、不改变方向 ID、不写审批状态。每次打开默认桌面画布，方向切换保留当前画布，关闭后焦点返回原入口。

卡片与沉浸视图共用同一个 `selectedPreviewId`。只有用户执行“选择此方案”时该值才改变；打开、导航、切画布和关闭都不能自动选择。沉浸视图不提供最终确认入口，用户仍须回到原“确认生成”按钮。加载失败或安全检查不通过的 SVG 可显示错误并继续导航，但不能选择。生成 SVG 以不可信输入处理：带脚本、事件属性、外链资源、外链导航或 `foreignObject` 的内容安全失败，不注入页面 DOM。

确认时控制面重新读取 Runner 当前 preview artifacts，校验 `previewId` 属于当前 `previewSetId`；D1 保存 approved 后，Runner 在 implementation 前再次复核。仅有浏览器选中状态不能越过门禁。

“换一组”会创建新的 preview set，并使旧方案 ID 与下游检查点失效，但不会启动 Codex。

## 3. 执行模式

| 模式 | 语义 | 检查点处理 |
|---|---|---|
| `continue` | 从首个未完成或失败位置继续 | 复用全部有效成功检查点 |
| `rerun` | 以当前需求完整重跑 | 清理旧工作区和检查点；重新生成并确认预览 |
| `step` | 只执行 `targetStage` | 前置检查点必须存在；目标已成功时直接复用 |

`targetStage` 可为 `mobile-spec`、`preview`、`implementation`、`build`、`deployment`。单步完成但未形成完整交付时，项目进入 `ready`；已经存在完整 deployment 检查点时应保留原 URL。

## 4. 检查点与失败续修

检查点与需求哈希绑定。需求不一致、产物缺失或审批 ID 过期时不能复用。

| 阶段 | 保存内容 | 再次执行行为 |
|---|---|---|
| Mobile Spec | 正式 marker、子阶段进度、尝试次数和 Gate 错误 | 复用已成功上游文档，只续修当前失败子阶段 |
| preview | manifest、set ID 和 3 份 SVG | 已确认且未失效时复用；换一组只清理本阶段及下游 |
| implementation | SiteManifest、生成文件账本和最近诊断 | 把结构或写入错误反馈给 Codex 定向修复 |
| build | 构建标记、真实日志和最近诊断 | 环境正常时从保存诊断继续，不先重复已知失败动作 |
| deployment | URL、健康检查时间和 evidence | 完整有效时复用原 URL；临时 URL 失效时只重做部署 |

单个 job 中的实现或构建修复最多三轮。失败上下文保留到同一需求的下一次继续或单步；只有 `rerun` 清除。

## 5. 项目状态与 Runner 状态

控制面项目状态：

```text
queued → dispatching → building → awaiting_approval
                         │              │
                         ├→ ready       └→ dispatching
                         ├→ paused
                         ├→ failed
                         └→ delivered
```

Runner job 使用 `queued`、`running`、`awaiting_approval`、`checkpointed`、`paused`、`failed`、`delivered`。控制面负责把 Runner 状态映射为 D1 项目状态，不直接把浏览器状态写入数据库。

## 6. 实时进度

- Runner 产生 progress、message 和 events；
- 控制站每 15 秒查询项目列表并同步运行中状态；
- Runner 最近保留 24 条事件，项目 API 返回最近 12 条，UI 展示最近 6 条；
- 进度值表示阶段里程碑，不等同于模型 Token 或线性耗时百分比；
- 主动回调只是加速路径，控制面轮询可以在回调受阻时收敛终态。

## 7. 暂停与并发

Runner 为 job 创建 `AbortController`，暂停会中断 Mobile Spec、Codex/OpenAI、npm、构建、Tunnel 和健康检查子进程，不是只修改 UI 状态。

全站共享 Runner 最多同时存在 2 个 `dispatching/building` 项目。名额由服务端原子更新控制；`awaiting_approval`、`ready` 和 `paused` 不占名额。

## 8. 阶段产物

| 阶段 | 展示格式 |
|---|---|
| mobile-spec | 5 份 Markdown |
| preview | 3 份 SVG 方案 |
| implementation | JSON/文本形式的生成清单 |
| build | 真实构建日志 |
| deployment | URL 与健康检查证据 |

产物接口必须同时校验用户所有权和原始需求哈希。完整字段见 [API 与数据](04-API与数据.md)。
