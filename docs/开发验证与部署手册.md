# 开发、验证与部署手册

## 1. 环境

- Node.js `>=22.13.0`
- npm 与可访问依赖 registry 的网络
- Web：vinext / Vite / Cloudflare Workers 兼容环境
- Runner：Node 文件系统、子进程、Codex CLI 或 OpenAI API
- 部署：正式 Provider，或仅用于验收的 cloudflared Quick Tunnel

## 2. 启动 Web

```bash
cd apps/web
npm ci
npm run dev
```

`.openai/hosting.json` 声明 Sites project 与 D1 `DB` binding。本地端口以开发服务器实际输出为准。

## 3. 启动 Runner

```bash
cd packages/codegen
npm ci
CODEX_RUNNER_TOKEN=... \
RUNNER_CALLBACK_TOKEN=... \
CODEX_BIN=/absolute/path/to/codex \
CODEX_WORKDIR=/absolute/path/to/repo \
CODEGEN_DISABLE_CALLBACK=1 \
CODEGEN_CONTROL_PLANE_URL=https://control.example \
CODEGEN_AUTO_PUBLIC_TUNNEL=1 \
CODEGEN_RUNNER_PORT=5174 \
node runner.mjs
```

OpenAI API 模式用 `OPENAI_API_KEY` 替代 `CODEX_BIN`。自动控制隧道模式下，Runner 会持续维护自身公网地址。本机浏览器点击“修复连接”时取得新地址，再由控制面验证并登记；`CODEX_RUNNER_URL` 只作为冷启动回退，派发仍使用匹配的 `CODEX_RUNNER_TOKEN`。

Quick Tunnel 验收还需 `CODEGEN_DEPLOYMENT_PROVIDER=cloudflare-quick-tunnel` 与 `CODEGEN_TUNNEL_BIN`。它不是生产配置。

macOS 验收机建议安装常驻服务，避免 Codex 会话或终端退出后 Runner 一起停止：

```bash
packages/codegen/scripts/install-runner-service.sh /tmp/mobile-build-runner.env
```

安装后由 `com.siteforge.runner` 自动启动和保活；环境文件权限为 `0600`，`cloudflared` 使用稳定副本，不再依赖 `/tmp` 生命周期。安装器会把当前 Node/npm 目录写入 LaunchAgent 的 `PATH`；可以用 `launchctl print gui/$(id -u)/com.siteforge.runner` 核对实际环境。

## 4. 验证命令

```bash
cd apps/web
npm run build
npm run lint
node --test tests/*.test.mjs

cd ../../packages/codegen
npm test
```

完整 E2E 需要：

1. Runner `/health` 返回 `ok: true`。
2. 创建一个从未预设过的需求。
3. progress 依次进入 Mobile Spec、implementation、build、deployment。
4. 控制站每 15 秒同步一次；message/events 来源于 Runner，而非前端定时器。
5. delivered 包含三项 evidence 和外部 HTTPS URL。
6. curl 请求交付 URL 返回非 5xx，页面文本匹配需求。
7. 再点“继续”不会重新运行已成功的 Mobile Spec、实现和构建；点“重跑”才从规格开始。
8. 分别点击规格、实现、构建、部署，验证前置检查和 `ready` 状态；点击步骤卡片可查看对应产物，`.md` 文件按 Markdown 渲染。
9. 让 Mobile Spec 的 Design/Tasks 或 Codex/构建产生一次可修复错误，再次点击“继续”或同一步骤；确认 Proposal 等已通过子阶段没有重跑，Codex 收到上次诊断，并且实时 message 显示“复用”或“修复”。
10. 对已成功步骤再次点击单步；确认没有新的模型调用、依赖安装或生产构建。完整交付项目应保留原 URL。
11. 阻断一次 Runner 主动回调后完成部署，再请求项目列表；确认控制面能从 Runner 拉取终态，将旧的 failed/paused 记录校正为 delivered。
12. 停止 Runner 控制隧道，触发一次派发错误；确认页面出现“修复连接”。点击后浏览器应通过本机恢复接口创建新地址，控制面校验实例编号与健康状态并登记，随后重新派发原任务。

## 5. 文档同步

```bash
node scripts/sync-docs.mjs
node scripts/check-docs.mjs
```

GitHub Actions 在每次非 `[docs-sync]` push 后执行同一流程，并将被推送的源提交 SHA 写入 `docs/实现状态快照.md`。随后产生带 `[docs-sync]` 的后续提交；该提交不会再次执行同步，避免循环。

仓库或分支必须允许 GitHub Actions 使用 `contents: write` 推送；受保护分支应为此工作流配置等价的允许规则。工作流只提交 `docs/` 下的生成变化，不自动提交应用源码。

自动流程不会理解所有产品决策。接口、用户流程、安全边界或路线图变化时，仍需更新对应叙述文档。

## 6. OpenAI Sites 发布

控制站线上地址：<https://mobile-app-build-mvp.long229260097.chatgpt.site>

发布步骤：

1. 完成 Web 构建、Lint、契约测试和必要 E2E。
2. 推送精确源码到 Sites 专用源仓库。
3. 使用 Sites packaging helper 打包 `dist`、hosting metadata 和 migration。
4. 保存站点版本，优先 owner-only 私有部署。
5. 轮询部署直到 succeeded。
6. 确认环境 revision 包含 Runner URL/token，且首页与关键 API 正常。

产品控制站托管与“用户生成页面的 DeploymentProvider”是两个系统。发布控制站不会自动把生成站点变成持久部署。

## 7. 数据库

当前 `ensureDatabase()` 对 users、sessions、projects 做 MVP 自举。Schema 变化应：

1. 修改 schema。
2. 生成并检查 migration。
3. 验证旧数据兼容。
4. 先发布兼容读写，再移除旧字段。

公开测试前必须取消请求路径动态 DDL，完全交由 migration 管理。

## 8. 上线检查

- 未登录项目 API 返回 401。
- 历史记录点击恢复正确项目；非进行中记录可以删除，进行中记录拒绝删除。
- 执行中显示百分比、当前 message，以及 Mobile Spec、Codex、写入、构建修复、部署事件列表。
- 输入框上方六个快捷按钮均不超过 4 个字；进行中禁用，非进行中可继续、重跑或单步执行。
- 成功步骤卡片可打开真实产物；规格包含 Proposal/Spec/Design/Review/Tasks 的 Markdown 预览。
- 失败规格再次执行时复用已通过的子阶段；失败实现/构建再次执行时使用保存的真实诊断，不先重复已知失败动作。
- 已成功单步再次点击只返回检查点复用消息；只有“重跑”允许清空工作区并完整重建。
- 部署阶段按地址和次数显示公网健康检查的 HTTP 状态或 DNS/连接错误；Quick Tunnel 固定使用 HTTP/2，系统 DNS 未同步时使用公共 DNS 结果验证同一 URL，临时地址仍不可用时在 120 秒总时限内最多自动更换 3 个地址，不重新执行已成功的规格、实现和构建。
- Runner 持续监控控制隧道进程并在失效后自动重建。页面连接类错误必须展示“修复连接”，点击后从本机 Runner 获取新地址，经服务端验证后登记并重派原任务。
- 每个用户前两个任务可并行派发，第三个任务在服务端返回 409；终态后释放名额。
- 浏览器无法 PATCH delivered。
- failed 项目没有 URL，delivered 项目三项 evidence 为真。
- `/preview`、localhost、控制站自身域名均不能成为交付 URL。
- 日志、文档、Git diff 中没有 Secret。

## 9. 回滚

- 控制站回归：重新部署最近通过验证的 Sites 版本。
- Runner 回归：停止新任务，恢复上一个 Runner 版本并保留 D1 终态。
- Token 变更：同步更新 Runner 与 Sites 环境并重新部署环境 revision。
- Runner 控制隧道失效：Runner 自动换址并登记，或由页面“修复连接”触发轮换；生成站点的临时 URL 失效时仍需重新执行部署单步，不能承诺恢复原 URL。
