# PRD / 技术方案上下文沉淀

将组件上下文整理成“快速定位代码 + 精准对接 PRD / 技术方案”的文档。目标不是复述已有文档，而是阅读代码、抽取真实链路，并把需求关键词映射到代码入口、链路边界、字段分流和风险点。

## 使用时机

使用本技能：

- 用户要求“整理上下文”“沉淀上下文”“按十项规范整理组件 docs”。
- PRD / 技术方案需要映射到代码入口、接口、状态、埋点、配置。
- 组件缺少上下文，需要根据现有代码逻辑新建 `docs/*.md`。
- 组件已有 `AGENTS.md`、`CLAUDE.md`、`docs/*.md`，但需要回到代码重新校准或补齐缺失逻辑。

不使用本技能：

- 用户只要解释某段代码，不要求沉淀文档。
- 用户要实现业务代码或修 bug；那时先按代码任务处理，必要时再更新上下文。

## 工作流

1. 先读组件入口和索引：`AGENTS.md`、`CLAUDE.md`、`docs/Index.md`、业务线 `Index.md`，只用于确认范围和已有路由。
2. 根据用户给出的组件、业务域、PRD 关键词或技术方案关键词，用 `rg` 搜索代码符号、接口名、字段名、通知名、埋点名、配置名。
3. 顺着代码建立证据链：入口类 -> 核心方法 -> Model / View / Cell / Controller / Service -> 接口 -> 状态 -> 埋点 / 通知 / 配置。
4. 只把代码能支持的事实沉淀进文档。已有文档只能作为线索，不能替代代码阅读。
5. 对业务名称、页面名称、跨 Pod 归属、服务端字段语义、PRD 口径不确定时，及时向使用者提问；不要用猜测补齐业务语义。
6. 保留现有合理拆分：组件大时用 `common.md` 做总路由，按业务域拆分子 md。
7. 将每份要沉淀的子文档统一为下面十项二级标题。
8. 更新路由入口：组件 `AGENTS.md`、`CLAUDE.md`、`docs/Index.md`、业务线 `Index.md`。
9. 校验每份文档正好 10 个 `##` 章节，并确认旧路径 / 旧口径无残留。

## 代码阅读方法

优先使用 `rg`，围绕以下线索递进：

| 目标 | 搜索线索 |
| --- | --- |
| 入口 | 组件名、Service、Manager、Controller、ViewController、Component、Adapter |
| 页面 | `ViewController`、`ViewLoader`、`View`、`Cell`、`Model`、`Factory`、`Strategy` |
| 接口 | `POST`、`GET`、接口路径、`Request`、`OperationManager`、`ParamsBuilder` |
| 状态 | `status`、`state`、枚举、`loadState`、`requestNextState`、`goToNextState` |
| 埋点 | `show`、`click`、`result`、`Statistics`、`track`、`event` |
| 通知 | `NSNotification`、`DSPC`、`postNotification`、`addObserver` |
| 配置 | `Apollo`、`DSServerConfig`、`NSUserDefaults`、`experiment`、`switch`、`config` |

阅读代码时记录：

1. 文件路径和类 / 方法名。
2. 字段从哪里来、传到哪里去。
3. success / failure 分支分别怎么收口。
4. 状态变化由谁触发，谁刷新 UI。
5. 生命周期里哪些观察者、定时器、请求需要清理。
6. 哪些逻辑跨 Pod，需要回到上游或下游确认。

## 需要及时沟通的情况

遇到以下情况，先问使用者，不要硬写：

- 代码里只有缩写、黑话或历史命名，无法确认对外业务名称。
- 同一个字段在不同链路含义不同。
- PRD 名称和代码目录 / 类名对应不上。
- 组件边界不清楚，可能属于其他 Pod。
- 服务端字段、实验位、埋点语义只能看到使用，无法确认业务含义。
- 多条链路都能解释同一个需求，无法判断主链路。

提问要短，优先给出已确认事实和需要确认的点。例如：“代码里 `xxx_flag` 同时影响 A/B 两处，我能确认它控制展示，但不能确认 PRD 里的业务名是‘新样式’还是‘实验版’，这里按哪个名称沉淀？”

## 十项模板

每份上下文文档使用相同二级标题，标题文本保持一致：

```markdown
## 1. 适用范围
## 2. PRD / 技术方案识别字段
## 3. 业务定位与职责边界
## 4. 快速代码定位
## 5. 架构主链路
## 6. 页面类对应关系
## 7. 接口与结果分流
## 8. 状态与生命周期
## 9. 交互、埋点与通知
## 10. 开关与配置
```

## 各章节写法

**1. 适用范围**
写清什么需求读它、什么需求不要读它、需要联读哪些文档。

**2. PRD / 技术方案识别字段**
用表格把关键词、服务端字段、类名、接口名、配置名映射到代码落点。

**3. 业务定位与职责边界**
说明组件在生命周期中的位置，上游 / 下游是谁，负责什么，不负责什么，跨 Pod 归属在哪里。

**4. 快速代码定位**
给类、目录、方法、入口文件。优先写能直接搜索的符号，少写抽象描述。

**5. 架构主链路**
用短链路或代码块描述入口、核心类、调用链路、数据流 / 状态流。

**6. 页面类对应关系**
写 VC / ViewLoader / View / Cell / Model 映射；没有页面时写服务类、模型、策略类映射。

**7. 接口与结果分流**
写接口名、参数来源、成功去向、失败收口、返回码或关键字段分流。

**8. 状态与生命周期**
写状态枚举、状态迁移、页面 / 组件生命周期、退出清理、观察者、定时器、请求取消。

**9. 交互、埋点与通知**
写按钮、滑块、弹窗、卡片、show / click / result、通知名、push、DSPC。

**10. 开关与配置**
写 Apollo、DSServerConfig、NSUserDefaults、实验位、服务端动态配置和本地默认值。

## 路由与命名

- 组件很大时，`AGENTS.md` 只做组件级路由，不承载大段业务细节。
- `docs/Index.md` 是 docs 内部子上下文索引；不要用 `README.md` 承接路由索引。
- 子文档按业务域命名，例如 `recommend.md`、`logic.md`、`after-serving.md`、`view/operation.md`。
- 新增、改名、迁移子文档后，同步更新组件 `AGENTS.md` 和业务线 `Index.md`。
- 上下文文件放到对应工程或组件的 `docs` 下。

## 写作约束

- 面向未来 Agent，句子要能指导定位代码和对接需求。
- 优先使用表格和短链路，避免长篇背景介绍。
- 缺失信息优先从代码补证据；代码只能证明技术行为时，不要擅自补业务名称。
- 对不确定业务语义要显式问用户；确认后再写入上下文。
- 不保留“AI 落地检查清单”作为独立章节；如有必要，把内容拆进对应十项。
- 不把 PRD 对接写成额外第 11 项；识别和对接能力沉到第 2、4、7、9、10 项。
- 不混淆相似字段体系，例如 Operation 的 `action_type` 和更多操作页的 `page_type`。

## 校验

整理后至少检查：

```bash
grep -n '^## ' path/to/doc.md
rg -n 'README\\.md|检查清单|PRD 对接检查|AI 落地检查清单' path/to/component/AGENTS.md path/to/component/docs path/to/business/Index.md
git -C path/to/repo status --short
```

验收标准：

- 每份目标子文档正好 10 个 `##` 章节。
- 组件入口能路由到所有已沉淀子文档。
- 业务线索引能路由到组件入口和关键子文档。
- `docs/README.md` 不作为子上下文路由索引；需要索引时使用 `docs/Index.md`。
- 旧口径如“PRD 对接检查”“AI 落地检查清单”不作为独立章节残留，应拆入十项结构。
- 只改文档时，不需要跑 iOS 编译，但最终说明要明确。
