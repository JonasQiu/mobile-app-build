# android-context-doc

为 Android 项目建立可复用、可索引、可维护的 Agent 上下文。目标不是写长篇白皮书，而是让后续 Agent 能从用户关键词、PRD 说法、类名或模块名快速找到正确代码、业务边界和修改风险。

## 核心原则

- 默认使用中文写文档；代码注释也用中文，除非项目已有相反约定。
- 所有结论优先来自本地文件证据：`AGENTS.md`、已有 docs、Gradle 配置、源码、注释、路由/SPI/服务入口和调用链。
- 不凭目录名或英文标识直接编造事实。无法确认的内容标记为 `待确认`，缺失但应补充的内容标记为 `待补充`。
- 保持渐进式披露：`AGENTS.md` 和 `index.md` 做导航，细节放入拆分文档。不要靠“何时读取本文”章节实现按需加载。
- `AGENTS.md` 只放规则、入口、索引和边界；详细架构、功能、术语、编码准则放入 docs。
- 每个拥有 `AGENTS.md` 的目录都应有同级 `CLAUDE.md` 软链接指向 `AGENTS.md`。若 `CLAUDE.md` 是真实文件或指向异常，不要静默替换，先报告冲突。

## 工作流选择

根据用户目标选择一种工作流：

| 用户目标 | 工作流 |
|---|---|
| 初始化项目文档、规范化全仓上下文、生成根和模块 docs 框架 | 全工程上下文 |
| 补充某个模块、页面、功能、流程、机制的上下文 | 功能/模块上下文 |
| 项目已有旧文档，需要迁移索引、对齐目录、比较差异 | 迁移和索引整理 |
| 改代码后影响流程、术语、依赖、边界、读取路径 | 变更后文档维护 |

开始前先按项目规则读取根 `AGENTS.md`，再读取目标目录最近的 `AGENTS.md`。命中功能关键词时，优先读取已有功能文档和索引，再读代码。

## 推荐目录结构

多模块 Android 项目优先使用以下结构：

```text
AGENTS.md
CLAUDE.md -> AGENTS.md
docs/
  architecture/index.md
  coding_standards/index.md
  glossary/index.md
  glossary/<term-slug>.md
<module>/
  AGENTS.md
  CLAUDE.md -> AGENTS.md
  docs/
    architecture/index.md
    biz/index.md
    biz/features/index.md
    biz/features/<feature>.md
    glossary/index.md
    glossary/<term-slug>.md
```

若仓库已有旧路径，如 `<module>/docs/<feature>.md`，不要直接移动。新索引应链接旧文档；只有用户明确要求迁移时才移动文件。旧版 `<module>/docs/features/` 为空时可清理；有内容时先索引或征得确认后迁移到 `<module>/docs/biz/features/`。

## 全工程上下文

1. 发现结构：
   - 读取根 `AGENTS.md`、`README*`、`settings.gradle(.kts)`、根构建文件、版本目录、`buildSrc` 和已有 docs。
   - 查找所有模块级 `AGENTS.md`、模块 build 文件和 docs。
   - Gradle 项目优先从 settings 推断模块列表，从 build 文件、imports、已有文档推断依赖关系。
2. 更新根上下文：
   - 根 `AGENTS.md` 包含工作准则、文档读取规则、术语读取规则、文档维护规则、根 docs 索引和模块索引。
   - `docs/architecture/index.md` 总结构建环境、模块依赖、工程框架索引。工程框架类概念写入 architecture，不写入 glossary。
   - `docs/glossary/index.md` 只做全局业务术语命中索引，术语详情放同目录详情文件。
   - 根 `docs/coding_standards/index.md` 是唯一的编码准则文档，描述仓库级生成规则、通用约束、命名、注释、兼容性要求。
3. 更新模块上下文：
   - 每个模块保持一致的 docs 二级目录结构。
   - 模块 `AGENTS.md` 描述职责、入口、关键类、文档索引、风险和读取路径。
   - 模块 docs 承载架构、业务索引、功能文档和模块术语。
   - 不在子模块下创建或维护 `docs/coding_standards/index.md`；模块特殊约束写入模块 `AGENTS.md` 的风险/约束章节，或写入相关功能文档的“注意事项”。
4. 输出时说明创建/更新了哪些文件、使用了哪些证据、哪些内容仍为 `待补充` 或 `待确认`。

## 功能/模块上下文

### 1. 识别 owner 模块

优先选择拥有主入口、权威已有文档或主要业务编排代码的模块。归属不清时，选择拥有业务入口的模块并标记 `待确认`。

### 2. 收集证据

至少覆盖：

- 入口类：Activity、Fragment、ViewModel、Presenter、Manager、单例、路由/SPI 实现。
- 核心数据流：数据请求、状态分发、渲染、缓存和降级。
- 对外接口：其他模块如何调用该能力。
- 生命周期：初始化、销毁、状态变化、登录态/订单态切换。
- 关键业务分支：订单类型、场景类型、开关、Apollo、灰度、端能力判断。

阅读策略：

1. 用用户关键词、产品词、类名、方法名搜索。
2. 从入口顺调用链读 2 到 3 层，不无限展开。
3. 对外工具类、Delegate、Helper、Service、Router、SPI 完整阅读。
4. 记录证据路径和关键方法，避免只写“参考某类”。

### 3. 写功能文档

功能文档默认放 `<owner-module>/docs/biz/features/<feature>.md`。旧文档可保留原路径并在新索引中链接。

推荐结构：

````markdown
# <功能名>

**关键词**: <技术类名>, <方法名>, <产品词>, <页面/UI词>, <业务场景词>

## 产品视角

<1-2 句话说明该功能对应的产品页面、交互或业务场景>

| PRD 中的 UI/功能描述 | 代码位置 |
|---|---|
| <产品语言，不写类名> | `<类名.方法名>` / `<路径>` |

## 典型改动场景

- 改 <产品功能> -> `<具体类/方法>`
- 新增 <产品能力> -> 参考 `<类名.方法名>` 的模式
- 改 <字段/文案/状态> -> `<数据来源或渲染位置>`

## 跨模块范围

| 模块 | 职责 | 关键入口 |
|---|---|---|

## 核心流程

```text
入口
  -> 调用链
  -> 数据/状态变化
  -> UI/服务结果
```

## 关键类与方法

| 类/文件 | 方法/字段 | 作用 |
|---|---|---|

## 数据、状态与开关

| 名称 | 来源 | 影响 |
|---|---|---|

## 注意事项

- <反直觉陷阱、兼容要求、新旧链路共存、ID/状态不可混用等>
````

写作要求：

- 关键词必须混合技术词和产品词，包含核心类名、高频对外方法、页面/UI 名称、PRD 常用说法。
- “产品视角”表格第一列禁止出现类名，第二列精确到方法或路径。
- “典型改动场景”至少 3 条，覆盖最常见 PRD 需求。
- “核心流程”用缩进伪代码或 Mermaid 写清楚主链路。
- 每篇功能文档都必须有“跨模块范围”，即使只涉及一个模块。
- 注意事项至少包含一个真实风险或容易踩坑点；没有证据不要硬编。

### 4. 同步索引

写完功能或模块文档后，同步更新：

- `<owner-module>/docs/biz/features/index.md`
- `<owner-module>/docs/biz/index.md`
- 必要时更新 `<owner-module>/AGENTS.md`
- 新增或澄清术语时，更新模块 glossary 和根 glossary
- 跨模块功能影响其他模块读取路径时，更新相关模块索引

索引优先用表格，包含关键词、范围和路径。关键词不要只放通用词，如“列表”“按钮”“页面”。

## 术语规则

- 根 `docs/glossary/index.md` 管跨模块业务术语；模块 `docs/glossary/index.md` 管模块局部术语。
- 索引只放术语、关键词、范围、详情路径；定义写入 `docs/glossary/<term-slug>.md` 或模块详情文件。
- 业务术语优先来自代码注释、已有文档、业务命名和用户描述，不要仅凭英文标识直译。
- 同名不同义时必须写清作用范围，并在索引中标出模块或功能。
- 工程框架、SDK、三方库、构建插件、监控框架等概念放 `docs/architecture/`，不放 glossary。

## 变更后文档维护

代码改动后，只在影响以下内容时更新文档：

- 可复用上下文、业务边界、功能流程、入口或降级逻辑
- 业务术语、状态语义、字段含义
- 模块依赖方向、模块职责、公共 API 或 SPI
- 仓库级编码准则、通用封装、禁用方式
- 文档读取路径、关键词路由、索引结构

不记录一次性调试日志、临时推理或任务流水。

## 安全规则

- 不整文件覆盖已有 `AGENTS.md` 或 docs；优先小范围编辑。
- 不删除、重命名公共 API，不做无关重构。
- 不静默移动已有文档，除非用户明确要求。
- 不编造精确构建版本、模块依赖或业务定义；必须从文件提取或标记 `待确认`。
- 不提交敏感信息，如签名文件、密钥、Token。
- 若项目规则禁止改构建版本号或要求检查特定开关，严格遵守项目 `AGENTS.md`。

## 完成检查

- 已读取根和目标目录最近的 `AGENTS.md`。
- 文档路径符合当前项目约定，新文档优先进入 `docs/biz/features/`。
- 关键词同时包含技术词和产品词。
- 产品视角、典型改动场景、核心流程、跨模块范围、注意事项齐全。
- 所有新增/修改文档均有索引入口。
- 新增/澄清术语已同步 glossary。
- 编码准则只维护根 `docs/coding_standards/index.md`；子模块不新增 `docs/coding_standards/`。
- 输出中列明 owner 模块、更新文件、证据来源、`待确认`/`待补充` 项。
