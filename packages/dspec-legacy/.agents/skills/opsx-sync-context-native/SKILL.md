将已完成变更的设计信息同步回项目 docs 文档。

**Input**: 变更名称（可选）。支持进行中的活跃变更和已归档的变更。若未指定，列出可用变更供选择。

---

## Steps

### 1. 确定目标变更

如果用户未指定变更名称：

```bash
openspec list --json
ls openspec/changes/archive/ 2>/dev/null | tail -10
```

用 **AskUserQuestion tool** 让用户从活跃变更和已归档变更中选择。显示格式：

```
活跃变更:
  - add-feature-x (native-sdd, 2/4 完成)

已归档变更（最近 10 个）:
  - 2026-06-10-api-exception-fallback
  - 2026-05-25-some-other-change
```

**IMPORTANT**: 不要猜测或自动选择，必须让用户确认。

### 2. 定位变更目录并读取设计文档

根据变更名称定位目录：
- 活跃变更：`openspec/changes/<name>/`
- 已归档变更：`openspec/changes/archive/<date>-<name>/`（若有多个日期匹配，让用户选择）

读取以下文件（存在则读取，不存在跳过）：
- `design.md` — 受影响模块/页面表、接口改动、配置开关
- `proposal.md` — 变更背景、能力范围（新增/修改能力列表）
- `specs/<capability>/spec.md` — 已确认的行为规格（WHEN/THEN），作为权威来源

若 `design.md` 不存在，仅依赖 `proposal.md` 推断影响范围。

### 3. 发现项目 docs 路由规则

**本步骤完全动态，不硬编码任何路径。**


然后读取项目上下文索引文件（常见位置，存在则读取）：
- `CLAUDE.md` 、 `AGENTS.md` — 文档索引表（关键词 → docs 路径映射）
- `README.md` — 项目结构说明

从这些文件中**提取路由规则**：即「哪些关键词/模块/类 → 对应哪个 docs 文件」。

对照 `design.md` 受影响模块表与提取到的路由规则，推断需要更新哪些 docs 文件。

**受影响模块在路由规则中没有明确映射时，跳过（不猜测，不新建文件）。**

**当本次需求需要回写的上下文与现存上下文文档模块不匹配时需要与用户确认回写方式，如新增文档、如何新增**

```
### 4. 读取需更新的 docs 文件

读取 Step 3 推断出的所有 docs 文件，了解现有内容和格式风格，用于：
- 幂等检查（避免重复写入相同内容）
- 对齐文档已有的格式风格

### 5. 分析并分级每个 docs 文件的变更候选项

对每个需要更新的文件，将候选变更分为两级：

**核心变更（必须同步，不询问用户）：**
- 已有初始化流程 / 生命周期列表新增步骤
- 已有关键机制的行为发生变化（如现有轮询终止条件新增判断分支）
- 已有注意事项章节需要补充的易错点 / 边界条件

**可选变更（由用户选择是否同步）：**
- 全新章节（现有文件中没有对应章节的新增内容）
- 新增配置开关的补充说明（若未关联到已有流程描述中）
- 监控 / 日志关键词说明
- 其他补充性内容（不影响对现有流程理解的背景信息）
- 新接口、字段、错误码、Mock、降级。
- 新状态、状态迁移、生命周期、观察者、请求清理、线程约束。
- 新页面、路由、通知、动态指令、跨 Pod 职责边界。
- 新埋点 show / click / result、日志字段。
- 新开关、Apollo、本地存储状态、服务端动态配置。
- PRD / 技术方案关键词到代码落点的新映射。

**始终跳过（不同步）：**
- 代码可以直接获取的信息（函数签名、字段名、文件路径）
- 纯实现细节（临时变量、循环逻辑、赋值操作）
- 已在文件中存在的相同内容（幂等检查）

**格式规则：**
- 保持文件原有格式风格（Markdown 表格保持表格，列表保持列表）
- 新增章节时，对齐现有章节的标题层级和写作风格
- 与文档整体语言风格保持一致（中文/英文）

### 6. 展示预览并让用户确认可选变更

**第一步：展示分级预览**

列出所有候选变更，标注级别：

```
## 即将更新 docs

### <docs-file-1>
[核心] ~ onCreate 关键流程第 7 步：checkOnlineStatusForCarpool()
[核心] ~ 注意事项：补充 checkOnlineStatusForCarpool() 触发条件
[可选] + 新增章节「<章节名>」— <内容摘要>
[可选] + 注意事项：<监控日志关键词说明>

### <docs-file-2>
[核心] ~ <已有机制描述> 补充超时终止条件
[可选] + 新增章节「<章节名>」
```

**第二步：针对可选变更，用 AskUserQuestion tool（multiSelect: true）让用户选择**

将所有 `[可选]` 项列为多选选项，用户可以勾选任意组合。

示例选项格式：
- `broadorder.md — 新增章节「播单引擎关键机制」`
- `broadorder.md — 注意事项：canRetryGetStriveStatus() 注意点`
- `orderrunning.md — 监控日志关键词说明`

若没有任何可选项，跳过此步直接执行。

**第三步：确认执行范围**

核心变更 + 用户勾选的可选变更 = 本次实际执行的变更集合。

### 7. 执行更新

逐文件使用 **Edit tool** 精准插入，**不使用 Write 整体覆盖**。

每次 Edit 后继续下一个文件，完成后在摘要中汇报结果。

若某文件已有相同内容（幂等检查），记录为「已是最新，跳过」。

### 8. 检查索引文件是否需要补充路由（可选）

若本次变更引入了新的模块/类/关键词，且这些词在项目索引文件（如 `CLAUDE.md`、`AGENT.md`）的路由表中没有对应条目，**提示用户**是否需要手动添加路由，说明建议追加的关键词和目标文件。

**不自动修改索引文件**，由用户决定。

### 9. 输出摘要

```
## Context Sync 完成

**变更来源:** <change-name>
**更新时间:** YYYY-MM-DD

**已更新文件:**
- <path/to/doc.md> — <具体做了什么>

**跳过文件（已是最新）:**
- <path/to/doc.md> — 内容已存在

**跳过模块（无对应 docs）:**
- <ModuleName> — 在路由表中无对应 docs 文件

**索引文件提示:**
- 建议在 CLAUDE.md、AGENT.md 中为 <关键词> 添加到 <docs路径> 的路由（或：无需更新）
```

## Guardrails

- **不猜测、不臆造**：只同步在 `design.md` / `proposal.md` / `spec.md` 中明确出现的信息
- **路由完全动态**：通过读取项目的 `CLAUDE.md` / `AGENT.md` / `README.md` 等索引文件推断文档路由，不硬编码任何项目特定路径或类名
- **最小化改动**：始终用 Edit 精准插入，保留文件现有全部内容
- **不镜像代码**：docs 记录的是「why + 关键约定 + 边界条件」，不是代码镜像
- **幂等**：若同一内容已存在，跳过（不重复写入）
- **核心变更不询问**：对现有流程的直接补充（步骤新增、条件变化）属于核心变更，直接执行，不要求用户确认
- **可选变更让用户选**：全新章节、补充说明等扩展性内容属于可选变更，用多选题让用户决定
- **归档超 30 天提示**：若变更归档超过 30 天，提示用户确认该变更是否已在代码中实际落地，再执行同步
- **路由未命中时跳过**：受影响模块在路由规则中无对应 docs，跳过（不新建文件），在摘要中注明
- **不自动修改索引文件**：只提示，由用户手动决定是否添加新路由条目
