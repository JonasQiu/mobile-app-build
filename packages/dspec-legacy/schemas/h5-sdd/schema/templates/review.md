# 一致性检查报告

> **检查目标**：以 `proposal.md` 为为什么做、做什么、不做什么的产品边界，以 `specs/**/*.md` 为受影响页面、详细需求与行为契约，以 `design.md` 为整体方案、语义化实现改动、接口说明与按需关键设计，检查三者的完整性、一致性和内容边界。
> 找出五类问题：**越界**、**矛盾**、**遗漏**、**不可追踪**、**模糊项**。
> **审查边界**：每个问题必须引用文件与位置，并指出应回改的 owning artifact；Review 不重新设计方案、不补写需求，也不覆盖上游事实。
> 仅当越界、矛盾、遗漏均为 0，且不存在未关闭的 High Severity 阻塞项时，文档最后一条状态行才可写为 pass。

---

## 越界（Out Of Scope）

> Specs 超出 Proposal 的“做什么 / 不做什么”边界，或者 Design 出现 Specs 未定义的页面或行为。

**检查清单**

- [ ] Specs 中的详细需求是否超出 Proposal 的高层交付范围？
- [ ] Design 中是否存在没有对应页面 Spec 的页面？
- [ ] Design 中是否引入了 Specs 未定义的行为？
- [ ] Design 中是否存在超出本次交付边界的接口调用或状态扩展？

<!-- 示例格式：
### OB-1 <问题标题>
- **类型**：越界
- **来源**：`specs/foo/spec.md` 第 12 行
- **描述**：该 Requirement 超出 Proposal 的“做什么 / 不做什么”边界。
- **Owning artifact**：`proposal.md` 或 `specs/foo/spec.md`，取决于确认后的产品边界。
- **建议**：修正 owning artifact 后重新 Review。
-->

无

## 矛盾（Conflict）

> Specs 与 Proposal 的为什么做、做什么、不做什么不一致，或者 Design 与 Specs 的页面、详细需求、行为、状态和验收场景不一致。

**检查清单**

- [ ] Specs 的目标、交付范围和非目标是否与 Proposal 一致？
- [ ] Spec ID、页面与共享规则域的归属是否唯一且不互相冲突？
- [ ] Design 的整体方案、语义化实现改动与关键设计是否表达同一条实现链路？
- [ ] Design 的目标用户、状态、生效条件、跳转逻辑和异常处理是否与对应 Specs 一致？
- [ ] Design 的接口、计算和降级是否实现 Specs 行为，且未反向改写需求？
- [ ] 接口说明是否与所引用的后端接口文档、技术方案或对齐记录一致？

<!-- 示例格式：
### CT-1 <问题标题>
- **类型**：矛盾
- **来源**：`design.md` 第 30 行
- **Specs 原文**：「入口：/home 页面点击卡片」
- **Design 原文**：「入口：/dashboard 页面侧边栏」
- **描述**：入口路由不一致。
- **Owning artifact**：`design.md`；若需求行为确已变化，则先回改对应 Spec；若为什么做、做什么或不做什么发生变化，则先回改 `proposal.md` 并重跑 Specs。
- **建议**：修正 owning artifact 后重新 Review。
-->

无

## 遗漏（Missing）

> Proposal 的“做什么”没有被 Specs 覆盖，或者 Specs 中的页面、详细需求与行为没有被 Design 完整覆盖。

**检查清单**

- [ ] Proposal 的每项“做什么”是否至少被一条 Spec Requirement 覆盖？
- [ ] 每个受影响页面是否都有且只有一个 `specs/<page-spec-id>/spec.md`？
- [ ] 每个归属 `shared-<domain>` 的跨页面规则是否都有且只有一个对应的共享 Spec？
- [ ] 同一跨页面规则是否只在归属 Spec ID 对应的文件中定义一次，没有复制到多个页面 Spec？
- [ ] 每个 Spec Requirement 是否直接记录需求改动点、需求范围、用户故事 / 预期结果和需求来源？
- [ ] 每个 Spec Requirement 是否有覆盖正常、边界与异常行为所需的 Scenario？
- [ ] Design 是否包含能独立说明端到端实现链路、主要模块职责和关键取舍的整体方案？
- [ ] 页面与 shared Specs 中每个 Requirement 是否至少被一个带语义标题的实现改动准确引用？
- [ ] 每个实现改动是否包含关联需求、页面 / 范围、代码落点、实现说明和验证重点？
- [ ] shared Requirement 是否保持 `shared-<domain>` 唯一归属，没有被复制为多个页面需求？
- [ ] 非显然技术决策是否使用语义标题，并只在跨模块契约、状态一致性、兼容降级或真实方案取舍存在时展开？
- [ ] 涉及接口时，接口说明是否列全所有接口，并通过接口名称与 METHOD + Path 区分后关联准确的 Requirement 或实现改动标题？
- [ ] 每个接口的请求参数、响应字段、错误码 / 异常处理、Mock、契约来源和对齐状态是否完整？
- [ ] 待对齐或阻塞的接口是否已在风险与待确认中记录差异、影响、Owner 和处理计划？
- [ ] 涉及共享状态、公共接口、跨页面生命周期、开关或兼容时，Design 是否说明跨页面影响与边界？
- [ ] 风险与待确认是否关联明确的页面、Requirement 或实现改动标题，并说明影响、处理计划、Owner 和是否阻塞？

<!-- 示例格式：
### MS-1 <问题标题>
- **类型**：遗漏
- **来源**：`specs/order-detail/spec.md`
- **描述**：该 Requirement 在 Design 中没有对应的语义化实现改动。
- **Owning artifact**：`design.md`。
- **建议**：在 `design.md` 中补充以业务动作或技术变化命名的实现改动，并准确引用该 Requirement。
-->

## 不可追踪（Untraceable）

> Specs 无法追踪到明确的需求来源，或者 Design 无法追踪到对应页面 Spec 与 Requirement。

**检查清单**

- [ ] 页面 Spec 是否通过稳定目录名和 H1 唯一标识页面，且没有一个页面拆成多个 Spec？
- [ ] Specs 中每个 Requirement 是否声明模块、适用时的产品组件路径和明确需求来源？
- [ ] Design 的每个语义化实现改动是否引用准确的 Spec 路径与具体 Requirement？
- [ ] Design 的每个接口是否引用准确的 Requirement 或实现改动标题，并提供可核对的契约来源？
- [ ] Design 的关键设计、验证和风险是否通过语义标题、页面或 Requirement 关联到对应实现？
- [ ] Design 的页面 / 范围是否沿用对应 Spec 的页面、shared 规则域及适用术语，且未将产品层级误作技术组件结构？
- [ ] Design 中每个技术决策是否都有 Specs 层面的需求依据？
- [ ] 是否存在描述过于抽象、无法判断覆盖哪条需求的场景？
- [ ] Specs 是否使用了与 Proposal 的“做什么 / 不做什么”不同的产品术语，导致语义映射断裂？
- [ ] Specs 场景标题是否清晰表达了与需求的对应关系？

<!-- 示例格式：
### UT-1 <问题标题>
- **类型**：不可追踪
- **来源**：`specs/bar/spec.md` 第 8 行
- **描述**：该 Requirement 描述过于抽象，且没有明确需求来源。
- **Owning artifact**：`specs/bar/spec.md`。
- **建议**：在 Spec 中补充具体需求、范围、来源和可验证场景。
-->

无

## 模糊项（Ambiguous）

> 需求存在，但描述不足以支撑开发或测试（缺少边界条件、状态定义、异常处理、验收标准，或存在多种理解方式）。

**检查清单**

- [ ] 是否存在缺少触发条件或边界值的场景描述？
- [ ] 是否存在状态定义不完整（缺少进入条件、退出条件、互斥关系）的描述？
- [ ] 是否存在对异常路径（网络错误、权限不足、数据为空等）缺少处理说明的场景？
- [ ] 是否存在可被多种方式理解的表述（如「适当的」「尽快」「部分情况下」）？
- [ ] 是否存在缺少明确验收标准、无法判断测试通过条件的需求？
- [ ] 接口说明中的请求参数、响应字段、错误码 / 异常处理是否明确必填性、数据类型、取值范围和前端处理？
- [ ] UI 交互细节（loading 态、空状态、超长文本截断）是否都有明确规定？

<!-- 示例格式：
### AM-1 <问题标题>
- **类型**：模糊项
- **来源**：`specs/baz/spec.md` 第 20 行
- **描述**：「用户点击后跳转」未说明跳转目标页面和条件。
- **风险**：开发和测试可能产生分歧，导致返工。
- **Owning artifact**：`specs/baz/spec.md`；若问题会改变为什么做、做什么或不做什么，则先回改 `proposal.md`。
- **建议**：补充跳转目标路由和触发条件；无法确认且构成阻塞时回到 Proposal 记录未决问题。
-->

无
